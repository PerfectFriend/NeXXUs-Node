# TON-контракты NeXXus (FunC) — СТАТУС: ПРОТОТИП / РЕФАКТОРИНГ (H-23)

> **Архитектурный статус: Контракты находятся в стадии активного рефакторинга перед деплоем в testnet.**
> До прохождения компиляции в Blueprint/Sandbox и устранения замечаний аудита H-23 контракты считаются экспериментальными прототипами.

## Анализ архитектурных задач (H-23):

1. **`NexxusEpochController.fc`**:
   * **Упаковка подписей**: Запись Ed25519 подписи занимает 256 (pubkey) + 512 (signature) = 768 бит. Стандартная ячейка TON вмещает 1023 бита. В одну ячейку физически помещается только 1 подпись. Для кворума $M \ge 2$ подписи переводятся на связанный список ячеек (`ref`) или словарь подписей (`HashmapE`).
   * **Валидация порога**: Требуется обязательная проверка инварианта $1 \le \text{threshold} \le N$ (не допускать $\text{threshold} = 0$).
   * **Domain Separation**: Подпись должна включать адрес самого контракта и network_id для защиты от cross-contract replay атак.
   * **Связка с залогами**: Параметры валидных аудиторов и залогов должны верифицироваться через кросс-контрактные вызовы к контракту залогов (`NexxusAuditorCouncilBond`), а не только через админ-транзакцию.

2. **`NexxusAuditorCouncilBond.fc`**:
   * **Учёт газа при депозите**: Депозит должен учитывать реальный баланс за вычетом газа транзакции, чтобы баланс книги учёта соответствовал фактическим нанотонам.
   * **Децентрализация Slashing**: Замена единоличного админского слэшинга на мультиподпись Совета или ZK-доказательство нарушения.
   * **Резервирование**: Использование `raw_reserve` перед выплатами для гарантированного покрытия баланса хранения контракта.

3. **`NexxusTreasuryVesting.fc`**:
   * **Обработка Bounce**: Реализация обработчика отскочивших сообщений (bounce handler), чтобы при неудаче Jetton-перевода батч не сгорал безвозвратно.
   * **Комиссии**: Проверка достаточного `msg_value` для покрытия комиссии форвардинга TEP-74.
